Complete search

The two rows at the top of your budget table have never been used. They are the ones that say a tiny n is permission to stop thinking.

The rows you have been skipping

Open the budget table and look at the top:

If n is up to…You can affordWhich usually means
10O(n!), O(n7)Try every permutation. Brute force everything.
20O(2n·n), O(n5)Try every subset. Bitmask DP.

Every instinct the last four lessons gave you says these are typos. O(n!) is the worst complexity class in the table. You spent lesson 0004 collapsing an O(n²) solution into O(n) and now the table is offering you factorial.

It is not a typo. It is the single most reliable signal in competitive programming, and it runs backwards from everything else you know.

The costing skill: where the cliff is

Before the technique, price it. Same habit as always: substitute the largest n and read off a number.

Two cliffs, and they are worth memorising because they are sharp:

n! dies at 13.   2n dies at 25. Below the cliff, brute force is free. Above it, no amount of cleverness in the loop body saves you.

Notice how much sharper these are than anything in lesson 0001. Going from n = 200 to n = 400 made an O(n²) solution 4× slower. Going from n = 20 to n = 21 makes a O(2n) solution twice as slow. One extra element doubles your entire runtime. That is what exponential means, and it is why the constraint is always tiny and always explicit.

The signal, and why it runs backwards

Lesson 0001 taught you that a large n forbids expensive solutions. The corollary is the thing nobody tells beginners:

A tiny n forbids cheap ones. If the setter had a clever O(n log n) solution in mind, why would they cap n at 20? They would not. A constraint of n ≤ 20 is the setter telling you that no clever solution exists, or that finding one is harder than checking all 1,048,576 cases. Stop looking.

This is the fingerprint. When you see n ≤ 20, n ≤ 24, or n ≤ 10, you have not been given a hard problem. You have been given permission to be stupid, quickly.

The Competitive Programmer's Handbook puts the trade honestly: “Complete search is a good technique if there is enough time to go through all the solutions, because the search is usually easy to implement and it always gives the correct answer.”1 Easy to implement and always correct. Under contest pressure those are worth more than elegance.

The technique: three shapes

USACO Guide names the whole family in one sentence: “In many problems (especially in Bronze) it suffices to check all possible cases in the solution space, whether it be all elements, all pairs of elements, or all subsets, or all permutations. Unsurprisingly, this is called complete search (or brute force), because it completely searches the entire solution space.”2

In Python you almost never write the generation yourself. itertools does all three in C.3

All subsets: 2n

“Choose any group of these items.” The classic: split n items into two piles as evenly as possible.

from itertools import combinations

best = 10**18
for k in range(n + 1):                 # every possible pile size
    for group in combinations(a, k):   # every pile of that size
        best = min(best, abs(sum(a) - 2 * sum(group)))

Summed over every k, that is 2n groups in total. Lesson 0006 shows the faster way to write the same loop.

All permutations: n!

“Put these in the best order.” Travelling salesman on 10 cities, arranging letters, assigning jobs.

from itertools import permutations

for p in permutations(a):              # n! orderings, lexicographic
    ...

The docs are precise about the count: “given by math.perm() which computes n! / (n - r)!”, and about the order: “The permutation tuples are emitted in lexicographic order according to the order of the input iterable.”3 That second fact is free correctness: sort your input and the output is already sorted, which is usually exactly what the problem wants printed.

All assignments: kn

“Give each of n items one of k labels.”

from itertools import product

for assign in product(range(k), repeat=n):    # k^n tuples
    ...

Where the Python tax lands here. itertools generates in C and lazily, so producing the cases is nearly free and uses no memory. The cost is your loop body, which is interpreted, and it runs 2n or n! times. So price the body, not the generation: a 20-operation body inside a 220 loop is 2·107 interpreted operations, which is already at the edge. Keep brute-force bodies brutally short. One caveat from the docs on product specifically: “Before product() runs, it completely consumes the input iterables, keeping pools of values in memory.”3

When the space is too big: prune it

Sometimes 2n or n! is too many, but most of those cases are obviously hopeless before you finish building them. Then you build solutions one piece at a time and abandon a partial solution the moment it cannot work. That is backtracking, and the abandoning is pruning.

CPH describes the move exactly: “The idea is to add ‘intelligence’ to the algorithm so that it will notice as soon as possible if a partial solution cannot be extended to a complete solution. Such optimizations can have a tremendous effect on the efficiency of the search.”1

def solve(i, state):
    if not viable(state):     # the prune: quit early, skip a whole subtree
        return
    if i == n:
        record(state); return
    for choice in options(i):
        solve(i + 1, apply(choice, state))

The honest catch: pruning does not change the complexity class. Worst case is still O(2n). It changes the constant, and for search problems the constant can be a factor of thousands. This is one of the few places in the sport where “it is still exponential” and “it now passes” are both true.

The escape hatch: meet in the middle

One thing worth recognising rather than mastering. If n ≤ 40 and you need subsets, 240 is far too many, but you can split the input in half, enumerate 220 subsets of each half, and combine. CPH: “using the meet in the middle technique, we can achieve a more efficient O(2n/2) time algorithm. Note that O(2n) and O(2n/2) are different complexities because 2n/2 equals √(2n).”1

You do not need to write one today. You need to recognise the fingerprint: n ≤ 40 with a subset-flavoured question means meet in the middle, the same way n ≤ 20 means plain subsets.
