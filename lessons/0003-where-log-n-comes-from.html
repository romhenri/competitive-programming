Where log n comes from

Lesson 0001 taught you to read a budget off the constraints. This one hands you the first technique that actually hits one — and shows you why the log factor is almost free.

The unpaid debt from lesson 0001

You learned that n ≤ 2·105 means “O(n log n) is intended”. You could look that up in the budget table and be right. But you had to take the log n on faith, and faith is not a skill.

So: log n is what you get when you repeatedly halve something. That is the whole definition you need. log₂ n is the number of times you can cut n in half before you reach 1.

Count it once by hand, for n = 1000:

1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1
# nine halvings. log₂(1000) ≈ 10.

Now the number that should genuinely surprise you:

nlog₂ nHalvings to get to one
1,00010Ten.
2·10518Eighteen.
10930Thirty.
101860Sixty.

Read the first and last rows together. n grew by a factor of a million million million; the work grew by a factor of six.

log n ≈ 20, for anything you will meet Treat the log factor as “multiply by about twenty”. It is closer to a constant than to a cost.

This is why the budget table is generous with O(n log n) and brutal with O(n²). Squaring multiplies your work by n. A log multiplies it by 20. They are not the same species of expensive.

The technique: binary search

Halving is not something that happens to you. It is something you do, and the doing has a name.

Finding a value in an array of n items costs O(n) — you check them all. Unless the array is sorted. As the Competitive Programmer's Handbook puts it: “if the array is sorted, the situation is different. In this case it is possible to perform the search much faster, because the order of the elements in the array guides the search.”1

Look at the middle element. It is either your target, too big, or too small — and in the last two cases half the array just became irrelevant. Repeat. Eighteen steps later you have searched two hundred thousand items.

You will not often write this by hand in Python. The standard library has it: bisect. But you need to be able to write it, because the second use of binary search — further down this page — has no library function.

The template that cannot loop forever

Binary search is notorious for off-by-one bugs. Learn one shape and reuse it. This one answers: what is the smallest x for which the check is true?

lo, hi = 0, n - 1          # hi must be a value known to be good
while lo < hi:
    mid = (lo + hi) // 2   # floors, so mid < hi whenever lo < hi
    if check(mid):
        hi = mid           # mid works — but maybe something smaller does
    else:
        lo = mid + 1       # mid fails — so does everything below it
answer = lo                # loop ends with lo == hi

It cannot hang, and the reason is worth twenty seconds of your attention: because // rounds down, mid is always strictly less than hi. So the hi = mid branch always shrinks the range, and the lo = mid + 1 branch always shrinks it too. Every iteration makes progress. That is the whole proof.

A C++ warning you can ignore. Tutorials will tell you to write lo + (hi - lo) // 2 to avoid integer overflow. Python integers do not overflow, so (lo + hi) // 2 is safe here. One less thing to remember.

In Python, reach for bisect first

For the plain “find it in a sorted list” case, the loop above is the wrong answer — it is 18 iterations of interpreted Python, and lesson 0001 told you what that costs. bisect does the same search in C:2

from bisect import bisect_left, bisect_right

a.sort()                       # O(n log n), and it runs in C
i = bisect_left(a, x)          # first index where a[i] >= x
found = i < len(a) and a[i] == x

count = bisect_right(a, x) - bisect_left(a, x)   # how many copies of x

bisect_left gives you the leftmost insertion point, bisect_right the rightmost. Almost every sorted-array question is one of those two, or their difference.

One trap in that module. insort() looks like the natural partner and is a TLE waiting to happen. The docs are blunt: “The insort() functions are O(n) because the logarithmic search step is dominated by the linear time insertion step.”2 Calling insort inside a loop over n items is O(n²) — the exact mistake lesson 0001 warned about with x in list, wearing a different hat.

The real prize: binary searching the answer

Everything above searches an array. That is the small use. Here is the one that wins contests.

You will meet problems where checking a candidate answer is easy, but finding the answer is not. Say a problem asks for the minimum time to finish some job. You have no idea how to compute it — but given a specific time T, you could easily check “is T enough?” in one O(n) pass.

Then you do not need to compute the answer. You can hunt it.

This works on one condition, and it is the only thing to remember: the check must be monotonic — once it flips from false to true, it stays true. USACO Guide states it exactly: “Binary search on the answer only works if the answer function is monotonic, meaning that it is always non-decreasing or always non-increasing.”3

false false false false TRUE TRUE TRUE TRUE
                        ↑
              you are hunting this edge

If more time is always at least as good as less time, the check is monotonic and you are in business. Concretely — CSES “Factory Machines”: n machines, machine i makes one product every k[i] seconds. What is the least time to make t products?

def enough(time):              # monotonic: more time never makes it worse
    made = 0
    for k in ks:
        made += time // k
        if made >= t:          # early exit; do not let it grow huge
            return True
    return False

lo, hi = 1, min(ks) * t        # hi: the slowest sane answer, always enough
while lo < hi:
    mid = (lo + hi) // 2
    if enough(mid):
        hi = mid
    else:
        lo = mid + 1
print(lo)

Now put your lesson-0001 hat on and price it. The check is O(n). The search runs it log(hi) times. Total: O(n log(hi)).

binary search = your check, × about 20 to 60 It converts “I can verify an answer” into “I can find the answer”, at almost no cost.

Where the Python tax lands. Here n is up to 2·105 and hi can reach 1018, so 60 iterations × 2·105 = 1.2·107 interpreted operations. Against a Python budget nearer 107/second, that is not comfortable — it is exactly the “borderline means fails” case. Two levers: set hi to a real bound like min(ks) * t rather than a lazy 1018, which often buys you several iterations for free; and return early from the check, as above. Count the iterations before you submit, do not hope.
