Two pointers

Binary search bought you a factor of twenty. This one buys you a factor of n — and teaches you to spot the nested loop that is secretly linear.

The collapse you have already seen

Lesson 0001 opened with this, and called it O(n²):

for i in range(n):
    for j in range(i + 1, n):
        if a[i] + a[j] == 0: ...

The fix there was a set. But a set only works because the target was exact. Change the question to “find a pair summing to at least x”, or “find the closest pair”, and the set is useless — the answer is not something you can look up.

Two pointers is the technique for that whole family. It is how a double loop over an array collapses to a single pass.

The idea, and the rule that makes it fast

From the Competitive Programmer's Handbook: “In the two pointers method, two pointers are used to iterate through the array values. Both pointers can move to one direction only, which ensures that the algorithm works efficiently.”1

Read the second half of that sentence again, because it is the entire lesson. The pointers never go backwards. That single restriction is what turns two nested loops into linear time.

Shape one: from the outside in

The array is sorted. One pointer starts at the smallest value, one at the largest. You are looking for a pair summing to x.

# a is sorted
lo, hi = 0, n - 1
while lo < hi:
    s = a[lo] + a[hi]
    if s == x:
        print("found"); break
    elif s < x:
        lo += 1        # need more: only bigger values remain, so move left up
    else:
        hi -= 1        # need less: move right down

Every branch either advances lo or retreats hi. They start n apart and meet, so the loop runs at most n times: O(n) after the sort. The sort dominates, so the whole solution is O(n log n) — comfortably inside the budget for n ≤ 2·105.2

Why is it correct to throw away a[lo] when the sum is too small? Because a[hi] is the largest value left. If a[lo] cannot reach x even paired with the biggest thing available, it cannot reach x with anything. It is eliminated forever, not just for this step. That is the same discarding-half instinct as binary search, applied one element at a time.

Shape two: the sliding window

Both pointers move the same way, one chasing the other. This is the shape for questions about contiguous stretches: a subarray summing to x, the longest run with no repeats, the cheapest window covering everything.

# positive values; find a contiguous subarray summing to exactly x
left = 0
cur  = 0
for right in range(n):
    cur += a[right]              # grow the window on the right
    while cur > x:
        cur -= a[left]           # too big — shrink it from the left
        left += 1
    if cur == x:
        print(left + 1, right + 1); break

The window only ever grows on the right and shrinks on the left. It never slides backwards, and that is the whole trick.

Counting it: the nested loop that is not O(n²)

Now the part that matters most for your mission, because it is a place your lesson-0001 instincts will actively mislead you.

Look at that code again. There is a while inside a for. Lesson 0002 taught you that nested loops multiply — n outer iterations × n inner iterations = O(n²). Apply that rule here and you will conclude the sliding window is quadratic, and you will be wrong.

Count it properly. Do not ask “how many times does the inner loop run per outer iteration?” — that question has no good answer, because sometimes it runs zero times and sometimes it runs a hundred. Ask instead:

How many times, in total, across the whole run? The right question for any loop whose inner cost varies.

Every pass of the inner while increments left. left starts at 0, only ever increases, and can never pass n. So the inner loop executes at most n times in total, for the entire algorithm — not per outer iteration. The outer loop is n, the inner is n in total, and the answer is n + n = O(n). Addition, not multiplication.

This style of counting has a name — amortised analysis — and the handbook files two pointers under exactly that heading.1 You do not need the theory. You need the reflex:

The reflex. When you see a loop nested inside a loop, before you write O(n²), check whether the inner loop has a counter that never resets. If it does, the two loops add instead of multiplying. If it resets on every outer iteration, they multiply and you were right the first time. This one distinction separates an O(n) solution from an O(n²) one, and the code looks nearly identical.

Which technique, given which budget

You now have two techniques and a budget table. Here is how they line up — this is the whole point of the last two lessons:

Budget saysReach forBecause
O(log n)Binary search aloneYou are hunting one value in a huge range.
O(n)Two pointers, sliding windowOne pass; each item enters and leaves once.
O(n log n)Sort, then two pointers or binary searchThe sort is the log; the scan after it is free.

Note the middle row against the budget table: two pointers is listed there under O(n), alongside prefix sums and greedy. You were reading that row before you knew what it meant.

The Python tax, honestly. Two pointers is a pure Python loop — there is no built-in to hide it in, so you pay full interpreted price for all 2n steps. Meanwhile sorted() runs in C. The consequence is genuinely counter-intuitive: at n = 2·105, an O(n log n) solution that pushes work into sorted() can beat an O(n) solution written as a hand-rolled loop on the clock. The complexity class still decides who survives a 10× bigger n — but do not assume the asymptotically better solution is the faster submission today. See the Python tax note.
