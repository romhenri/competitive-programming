Course · Lesson 0001

From n to your time budget

The constraints at the top of a problem are a message from the setter telling you which algorithm they had in mind. This lesson teaches you to read it.

The situation

You open a Codeforces problem. Somewhere near the bottom of the statement, in small type:

1 ≤ n ≤ 200000

Most beginners skim past this. It is the single most informative line in the problem. It is the setter quietly telling you “the solution I want runs in about n log n; do not bother submitting a double loop.”

Learning to hear that takes exactly two facts.

Fact one — the machine's budget

A judge server runs on the order of 108 simple operations per second. Time limits are typically 1–2 seconds. So your whole solution gets a budget of roughly a hundred million operations.1

108 operations ≈ 1 second Everything in competitive programming hangs off this number.

That is not a lot and it is not a little. It is enough to touch two hundred thousand items five hundred times each. It is nowhere near enough to compare every pair of a million items.

Fact two — complexity is a recipe for counting

“Time complexity” sounds abstract. Operationally it is not. It is a formula with n in it, and you use it by substituting the largest n the problem allows and reading off a number.

Take a concrete problem: given a list of numbers, does any pair sum to zero? Here is the obvious solution:

# Check every pair.
for i in range(n):
    for j in range(i + 1, n):
        if a[i] + a[j] == 0:
            print("YES"); return

The inner line runs once per pair. There are about n²/2 pairs. We call this O(n²) — read aloud as “order n squared”. The notation deliberately throws away the /2 and any constant: at the scale we care about, only the shape of the growth matters.2

Now substitute. That is the whole skill:

If n is…n² is…Verdict at 108/sec
1,000106Instant. 1% of budget.
10,000108Right at the edge. Nervous.
200,0004·1010400× over budget. TLE.

Same code, same correctness. The constraint alone decides whether it is a solution or a wasted submission. And notice what changed between rows: n grew 200×, but the work grew 40,000×. That is what squaring does, and it is why n ≤ 200000 is a hard no to double loops.

The fix, for the record, is one line and it is O(n):

seen = set()
for x in a:
    if -x in seen:          # set lookup: O(1), not O(n)
        print("YES"); return
    seen.add(x)

2·105 operations instead of 4·1010. Same answer, 200,000× less work.

Putting it together

You now have the loop that every competitive programmer runs before writing code:

  1. Read the largest n from the constraints.
  2. Ask what complexity fits inside 108 for that n.
  3. Only then pick an algorithm.

Step 2 is a lookup, and you should not derive it under contest pressure — that is what the Complexity Budget Table is for. Print it. But two rows are worth burning into memory right now, because they cover most of what you will meet:

ConstraintIntended solution
n ≤ 1000O(n²) — a double loop is expected. Stop looking for something clever.
n ≤ 2·105O(n log n) — sort it, or use a set/heap. A double loop will TLE.

You write Python, so add a tax. The 108 figure assumes C++. A Python loop manages closer to 107 operations per second. But work you push into a built-in — sorted(), sum(), in on a set — runs in C at nearly full speed. Rule of thumb: when the table says “borderline”, in Python read “fails”. More in the reference sheet.
