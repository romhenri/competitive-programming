Counting loops

Lesson 0001 told you what you're allowed to spend. This one tells you what your code actually costs. Three rules, and you can price almost any contest solution on sight.

Last lesson you read n ≤ 200000 and concluded “O(n log n), no double loops”. Useful — but only if you can look at your own code and say which class it lands in. That's this lesson.

Rule 1 — a loop costs iterations × body

Start with the only thing you ever really count: how many times does the innermost line run?

total = 0
for x in a:          # n iterations…
    total += x       # …of a body costing O(1)

n iterations of constant work: O(n). The total = 0 before the loop is O(1) and vanishes — a single fixed cost never changes the growth shape.1

Rule 2 — nesting multiplies

for i in range(n):        # n times…
    for j in range(m):    # …m times each
        grid[i][j] = 0

n × m — and when both bounds are n, O(n²). Nesting is multiplication, always. Three levels deep is O(n³).

Watch for two different variables. Contest problems love giving you n items and q queries. O(n·q) with n, q ≤ 105 is 1010 — dead — even though neither number looks alarming on its own. Always substitute both.

Rule 3 — sequential takes the max

for x in a:              # O(n)
    ...
for i in range(n):       # O(n²)
    for j in range(n):
        ...

One after the other, so the cost is n + n². But at n = 105 that's 105 + 1010 — the first term is a rounding error. Sequential blocks: keep the worst, discard the rest. This is O(n²).

nested → multiply  ·  sequential → take the max Almost all complexity analysis is these two moves, applied repeatedly.

The trap: loops that depend on the outer variable

This one catches everybody. The inner loop doesn't run n times — it runs a different number of times on each pass:

for i in range(n):
    for j in range(i + 1, n):    # n-1, then n-2, then n-3, …
        check(a[i], a[j])

The total is (n−1) + (n−2) + … + 1 = n(n−1)/2, which is about n²/2.

So is it O(n²) or O(n²/2)? O(n²). Big O throws away constant factors, and here's the practical reason why: halving 1010 still leaves you 50× over budget. Being twice as fast never rescues the wrong complexity class — only changing the class does.

This shape — “every pair, without repeats” — is extremely common. Learn to recognise it on sight and price it at O(n²) without doing the arithmetic.

The Python trap: the loop you didn't write

Rule 1 said “iterations × body”. Everything above assumed the body was O(1). In Python it very often isn't, because a single innocent line hides a loop:

LineCostWhy
x in my_listO(n)Scans until found. A loop in disguise.
x in my_setO(1)Hashes straight to the slot.
my_list.count(x)O(n)Scans the whole thing, every time.
sorted(a)O(n log n)It's a sort. Cheap — but not free.
a[i:j]O(j−i)Slicing copies. It does not view.
a.pop(0)O(n)Shifts every remaining element left.

So this loop is not O(n):

seen = []
for x in a:
    if x in seen:        # O(n) hiding inside an O(n) loop
        return True
    seen.append(x)

It's O(n²). Change [] to set() — one character of difference in how it reads — and it becomes O(n). This is the most common way a Python competitor TLEs a solution that looks obviously linear.

A taste of O(log n)

Not every loop runs n times. Watch the counter:

while n > 1:
    n //= 2      # 1000 → 500 → 250 → 125 → … → 1

Starting at a million, that's 20 iterations. At a billion, 30. Halving until you hit 1 is O(log n) — and log n is so small it's almost free. This is where binary search gets its power, and it's the subject of a later lesson.
